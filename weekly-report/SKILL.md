# /weekly-report — 주간 현장실습 업무 보고서

사용자가 준 일일 실무 기록을 4단계 구조의 주간 보고서로 바꾼다. 초안 → humanize 윤문 → 규칙 검사 → 저장 순서로 진행한다.

- 경로 스크립트: `/Users/smk/projects/my-agent-skills/weekly-report/scripts/report_path.py` (아래에서 `$PATHS`)

## 0. 저장 폴더

보고서는 **저장 폴더**에 `N주차-MMDD.md`로 저장한다. 폴더는 설정 파일(`~/.config/weekly-report/config.json`)에 들어 있어서 사용자가 다시 바꿀 때까지 유지된다. 기본값은 `/Users/smk/projects/weekly-reports`다.

```bash
python3 $PATHS --out-dir               # 현재 저장 폴더
python3 $PATHS --set-out-dir <경로>    # 변경 (없으면 만든다)
```

`$ARGUMENTS`에 `--out <경로>`가 있거나 사용자가 "저장 폴더를 ~로 바꿔줘"라고 하면 먼저 바꾸고 바뀐 경로를 한 줄로 알린다. 폴더만 바꾸고 기록이 없으면 거기서 끝낸다. 예전 폴더의 보고서는 옮기지 않는다.

## 입력
$ARGUMENTS

- 비어 있으면 "이번 주 일일 기록을 붙여넣어 주세요 (예: `- 7/13: 팀 데일리스크럼 참석, ...`)"라고 안내하고 멈춘다.
- `.txt`/`.md` 경로면 `Read`로 읽는다.
- `/project-report`가 만든 프로젝트 노트를 주면(저장 폴더는 `python3 /Users/smk/projects/my-agent-skills/project-report/scripts/collect_sessions.py --notes-dir`로 확인) `## 날짜별 작업 로그`에서 그 주 날짜만 골라 입력으로 쓴다. 노트가 여러 개면 날짜순으로 합친다. 같은 노트의 `트러블슈팅 · 의사결정`과 `기술 스택`은 2단계(기술 선택 이유)와 3·4단계(결과·역량)의 근거로 쓴다. 노트에 있는 수치만 옮기고 새로 만들지 않는다.

## 1. 초안 작성

### 가장 중요한 원칙: 기록에 있는 것만 쓴다
보고서는 사용자 이름으로 학교·기관에 제출된다. 기록에 없는 작업(예: 기록에 없는데 "서버 최적화"를 넣는 것)이나 수치를 지어내면 사용자가 곤란해진다. 기록의 항목을 단계에 배치하고, 이유·인과관계는 기록에서 자연스럽게 읽히는 만큼만 풀어 쓴다. 4단계의 "역량 강화" 문장도 그 주에 실제로 한 일에서 끌어낸다.

### 형식 (예시와 같은 모양)
```
[한 주 업무를 한 줄로 요약한 제목]

1. [업무의 시작과 확장] {소제목}
{본문 2~4문장}

2. [핵심 개념 학습 및 비교 분석] {소제목}
{본문}

3. [데이터 기반의 분석 및 실무 적용] {소제목}
{본문}

4. [성과 도출 및 직무 역량 강화] {소제목}
{본문}
```

| 단계 | 담을 내용 |
|---|---|
| 1. 업무의 시작과 확장 | 스크럼·온보딩·환경 설정·목업/UI 설계 등 그 주의 출발점 |
| 2. 핵심 개념 학습 및 비교 분석 | 비즈니스 로직 분석, 기술 스택을 고른 이유(예: 일정이 짧아 Supabase 채택), DB 설계·권한 연동 |
| 3. 데이터 기반의 분석 및 실무 적용 | 실제 구현한 화면, 데이터 가공·자동 매칭 로직, 예외 처리, 파일 입출력(엑셀 다운로드 등) |
| 4. 성과 도출 및 직무 역량 강화 | 상황에 맞는 기술 선택, 프로세스 효율화, 목표 직무(백엔드/컴퓨터공학)와 이어지는 역량 |

어떤 단계에 해당하는 기록이 적은 주라도 4단계는 모두 쓴다. 대신 짧게 쓰고 없는 일을 채워 넣지 않는다.

### 문체
- `~했다` 체의 담백한 서술. 개발자가 아닌 사람(지도교수·담당자)이 읽어도 이해되게 쓴다. 기술 용어는 처음 나올 때 한 번 풀어 준다(예: "클라우드 데이터베이스 도구인 Supabase").
- 과장·딱딱한 표현을 피한다: `~을 단행하였다`, `~에 착수하였다`, `파이프라인 구축`, `대폭`, `크게 강화`, `최선의 대안` 같은 말.
- 작업 순서와 인과를 드러낸다. 순서가 뚜렷하면 `목업 개발 ➡️ 기능명세서 작성 ➡️ 실제 개발`처럼 ➡️로 이어 쓴다(사용자가 정한 표기다).

### 금지어
`IPP`, `월차`, `연차`, `휴가`, `재택`은 쓰지 않는다. 쉰 날은 아예 언급하지 않고, 재택으로 한 일은 장소 언급 없이 한 일만 쓴다.

## 2. humanize 윤문

초안을 `humanize-korean:humanize-korean` 스킬로 넘긴다(`/humanize`는 사용자만 부를 수 있는 명령이라 본체 스킬을 직접 부른다). args는 다음처럼 준다:

```
{초안 전문}

장르: 리포트
보존 지시: 첫 줄 제목, "1. [업무의 시작과 확장]"~"4. [성과 도출 및 직무 역량 강화]" 네 줄의 단계 표기, ➡️ 순서 표기는 사용자 지정 형식이므로 그대로 둔다. ~했다 체 유지.
```

humanize가 경로(light/standard/heavy)를 알아서 고른다. 사용자가 "정밀하게"라고 했으면 `--strict`를 붙인다.

## 3. 규칙 검사

윤문본을 파일로 저장하고(humanize의 `final.md`를 써도 된다) 검사한다. 제출 시스템마다 바이트 계산이 다른데, UTF-8(한글 3바이트)이 가장 엄격하므로 이 기준을 통과하면 어디서든 통과한다.

```bash
python3 -c "
import sys,re
t=open(sys.argv[1]).read().split('<!-- HUMANIZE-SUMMARY')[0].strip()
b=len(t.encode()); print(f'{b} bytes (UTF-8) / 4000', 'OK' if b<=4000 else 'OVER')
bad=[w for w in ['IPP','월차','연차','휴가','재택'] if w in t]; print('금지어:', bad or '없음')
miss=[s for s in ['업무의 시작과 확장','핵심 개념 학습 및 비교 분석','데이터 기반의 분석 및 실무 적용','성과 도출 및 직무 역량 강화'] if s not in t]; print('빠진 단계:', miss or '없음')
" <파일경로>
```

걸린 항목이 있으면 직접 고치고 다시 돌린다. 4,000바이트를 넘으면 3단계의 세부 나열부터 줄인다. 금지어나 빠진 단계 표기는 해당 부분만 고친다. 윤문본 전체를 다시 쓰지는 않는다.

## 4. 저장

파일명의 **MMDD는 입력 기록의 첫 날짜**(그 주의 시작, 예: 7/13 → `0713`)다. **주차 N**은 사용자가 "3주차"처럼 말했으면 그 값을 `--week`로 넘기고, 아니면 스크립트가 정한다(같은 MMDD 파일이 있으면 그 주차, 없으면 폴더의 마지막 주차 + 1).

```bash
python3 $PATHS --start 0713 [--week 3]
# → {"path": ".../3주차-0713.md", "week": 3, "exists": false, "first_report": false}
```

- `first_report`가 true이고 사용자가 주차를 말하지 않았으면, 저장 전에 "몇 주차인가요?"라고 한 번 묻는다. 폴더가 비어 있으면 스크립트는 1주차로 잡는데, 실습 중간부터 쓰기 시작한 경우 번호가 계속 어긋나기 때문이다.
- `exists`가 true면 같은 주 보고서를 다시 만든 것이다. 사용자가 손본 파일일 수 있으니 덮어쓸지 먼저 묻는다.
- 파일에는 최종 보고서 본문만 넣는다. 검사 결과 줄과 humanize 요약 주석은 넣지 않는다.

## 5. 결과 전달

1. 검사 결과 한 줄: `{N} bytes / 4000 · 금지어 없음 · 4단계 OK · humanize {경로}, 변경률 {X}%`
2. 저장한 파일 경로 (`…/3주차-0713.md`)
3. 최종 보고서를 코드 블록으로 준다. 사용자가 그대로 복사해 제출 칸에 붙인다. humanize 요약 주석은 빼고 준다.
4. 기록이 부족해 짧게 쓴 단계가 있으면 어느 단계인지 한 줄로 알린다. 내용을 보태고 싶으면 그 주의 기록을 더 달라고 한다.
