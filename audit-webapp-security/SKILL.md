# 웹서비스 코드베이스 보안 감사

코드에서 실제로 도달 가능한 공격 경로를 추적하고, 재현 근거가 있는 문제만 발견사항으로 보고하라. 체크리스트를 채우는 데 그치지 말고 입력점부터 보호 자원까지 끝까지 추적하라.

## 필수 참고자료

감사를 시작하기 전에 다음 자료를 모두 읽어라.

- 세부 점검 관점과 공격 시나리오: [references/review-checklist.md](references/review-checklist.md)
- 심각도·증거·보고 형식: [references/report-format.md](references/report-format.md)

## 기본 원칙

- 사용자가 수정까지 명시하지 않으면 읽기·진단만 수행하라.
- 기존 작업 트리와 사용자 변경을 보존하라.
- 비밀값, 개인정보, 토큰 원문을 출력하지 말고 파일명·변수명·마스킹된 형태만 보고하라.
- 테스트·로컬 환경에서만 안전한 동적 검증을 수행하라. 운영 공격, 대량 요청, 데이터 변경, 계정 잠금 유발, 외부인 대상 요청을 하지 마라.
- 자동 스캐너 결과를 그대로 발견사항으로 채택하지 마라. 코드 경로와 방어 계층을 수동 검증하라.
- 보안 권고와 실제 취약점을 구분하라. 공격 가능성이 입증되지 않은 하드닝 제안은 별도 섹션에 둬라.
- 확인하지 못한 범위를 “문제 없음”으로 표현하지 마라.

## 1. 범위와 실행 모드 확정

1. 저장소 루트, 적용되는 `AGENTS.md`·프로젝트 지침, 기술 스택, 실행·테스트 명령을 확인하라.
2. 사용자 요청을 다음 중 하나로 분류하라.
   - `audit`: 진단과 보고만 수행
   - `audit-and-fix`: 검증된 발견사항을 수정하고 회귀 테스트
   - `targeted`: 인증, 업로드, 특정 API 등 지정 영역만 집중 점검
3. 범위에 프론트엔드, API, 백그라운드 작업, DB 마이그레이션, 인프라 설정, CI, 외부 연동이 포함되는지 기록하라.
4. `git status`를 확인하고 사용자 변경과 감사 작업을 분리하라.

## 2. 시스템과 공격표면 지도 작성

다음 항목을 빠르게 목록화하라.

- 프로세스·서비스·데이터 저장소와 신뢰 경계
- 모든 HTTP·WebSocket·웹훅·업로드·CLI·스케줄러 입력점
- 인증 방식, 세션·토큰 수명, 역할, 테넌트·프로젝트 경계
- 민감 자산: 개인정보, 급여, 인증정보, 파일, 관리자 기능, 외부 API 토큰
- 브라우저, 내부 사용자, 외부 사용자, 관리자, 서비스 계정, 제3자 공급자
- 인터넷으로 나가는 요청과 사용자가 목적지를 통제할 수 있는 경로

발견된 경계마다 “누가 어떤 입력으로 어떤 자원에 도달하는가”를 한 문장으로 표현하라.

## 3. 넓은 정적 점검 수행

가능한 경우 다음을 병렬로 확인하라.

- 라우트·컨트롤러·서버 액션과 인증·권한 가드 누락
- 동적 SQL·셸·템플릿·HTML·URL·파일 경로 구성
- 쿠키, CORS, CSP, 보안 헤더, 리디렉션, 캐시 설정
- 업로드 크기·형식·내용 검증과 다운로드 권한
- 토큰·비밀정보·개인정보의 저장, 로그, 응답 직렬화
- 잠금파일 기반 의존성 감사와 위험한 설치·빌드 스크립트
- 디버그 모드, 기본 비밀번호, 샘플 키, 과도한 권한
- 테스트가 보장하는 보안 불변조건과 빠진 음성 테스트

검색은 우선 `rg`와 저장소의 기존 도구를 사용하라. `.env`, 키 파일, 인증서 내용을 통째로 출력하지 말고 파일 존재와 키 이름만 확인하라. 의존성을 설치·업데이트하지 말고 잠금파일을 변경하지 마라.

## 4. 다관점 심층 검토 수행

[review-checklist.md](references/review-checklist.md)의 모든 관점을 적용하되, 현재 스택에 존재하지 않는 항목은 `해당 없음`과 근거를 남겨라.

특히 다음 교차 관점을 놓치지 마라.

- 공격자 관점: 외부 비인증자, 일반 사용자, 다른 사용자의 계정, 내부자, 외부 프로젝트 참여자
- 방어자 관점: 예방, 탐지, 복구, 감사 추적
- 데이터 관점: 생성, 조회, 수정, 삭제, 백업, 로그, 내보내기
- 수명주기 관점: 가입, 초대, 권한 변경, 비활성화, 비밀번호 초기화, 토큰 폐기
- 운영 관점: 개발·테스트·운영 차이, 프록시·CDN·클라우드 설정
- 시간 관점: 재전송, 중복 이벤트, 경쟁 상태, 만료 경계, TOCTOU

## 5. 고위험 흐름을 종단 추적

최소한 다음 유형의 흐름을 UI 또는 외부 입력부터 DB·파일·외부 서비스까지 추적하라.

1. 로그인·로그아웃·비밀번호 변경·초기화
2. 역할 변경과 관리자 전용 동작
3. 다른 사용자의 객체를 ID로 조회·수정·삭제하는 동작
4. 파일 업로드·미리보기·다운로드·원본 삭제
5. 외부 URL 요청, OAuth 콜백, 웹훅, 서명 검증
6. 개인정보·급여·인증문서 등 고민감 데이터 처리
7. 결제·정산·연차·승인 등 금전 또는 권리와 연결된 비즈니스 로직

각 흐름에서 입력 검증, 인증, 객체 권한, 상태 전이, 트랜잭션, 출력 인코딩, 로그 노출을 확인하라.

## 6. 역할·객체 권한 행렬 검증

실제 역할을 행으로, 핵심 자원 작업을 열로 둔 행렬을 만들라. 각 셀에서 허용 근거 또는 거부 근거를 코드로 확인하라.

최소한 다음 부정 시나리오를 검증하라.

- 비인증 요청
- 사용자 A가 사용자 B의 자원 ID 사용
- 낮은 역할이 관리자 API 직접 호출
- 프로젝트·테넌트·조직 경계를 넘는 ID 사용
- 숨겨진 UI를 우회한 API 직접 호출
- 비활성·삭제·권한 강등 계정의 기존 토큰 재사용

UI에서 버튼을 숨기는 것만으로 권한이 보호된 것으로 판단하지 마라.

## 7. 안전한 동적 확인 수행

실행 중인 로컬 또는 명시된 테스트 환경이 있을 때만 동적 검증을 수행하라.

- 한 번에 하나의 가설만 검증하고 최소 요청을 사용하라.
- 실제 사용자 데이터 생성·메일 발송·외부 파일 삭제를 피하라.
- 테스트 계정과 테스트 데이터를 사용하라.
- 상태를 변경했다면 원복 가능성과 원복 결과를 기록하라.
- 빌드, 타입 검사, 보안 관련 단위·통합 테스트를 실행하라.
- 네트워크가 필요한 감사 명령은 권한과 환경 제한을 먼저 확인하라.

동적 검증이 불가능하면 정적 근거의 한계를 명시하라.

## 8. 발견사항을 반증한 뒤 확정

발견 후보마다 다음 질문에 답하라.

1. 공격자가 해당 입력을 실제로 통제할 수 있는가?
2. 취약 코드까지 도달하기 전에 다른 검증이나 권한 검사가 있는가?
3. 보호 자원 또는 신뢰 경계를 실제로 넘는가?
4. 재현 조건이 기본 설정 또는 현실적인 배포 설정에 존재하는가?
5. 테스트나 프레임워크 기본 동작이 공격을 이미 차단하는가?

하나라도 불명확하면 신뢰도를 낮추고 확인 필요 사항으로 보고하라. 동일 원인의 반복 사례는 하나의 발견사항으로 묶고 영향 범위를 나열하라.

## 9. 독립적인 2차 감사 수행

수정 모드에서는 1차 감사와 수정이 끝난 뒤 반드시 탐색 순서를 바꾼 2차 감사를 수행하라. 1차 검색어와 발견사항만 재확인하는 것은 2차 감사가 아니다.

1. 라우트 중심으로 봤다면 2차에는 엔티티·외래키·외부 자원 중심으로 역추적하라.
2. 모든 `eager` 관계, 컨트롤러의 엔티티 직접 반환, 객체 spread를 찾아 응답 경계를 전수 확인하라.
3. 사용자·프로젝트·조직 삭제를 시작점으로 모든 최신 엔티티, self-FK, `RESTRICT`·`CASCADE`·`SET NULL`, 외부 파일 삭제 작업을 영향 그래프로 확인하라.
4. 소스 마이그레이션 목록만 보지 말고 가능하면 적용 DB의 pending 상태, nullability, 실제 `delete_rule`을 읽기 전용 쿼리로 확인하라.
5. 로그인 외에도 현재 비밀번호 확인, 증명서 발급, 토큰 발급, 메일 재발송 등 동일한 비밀·비용 자원을 검증하는 우회 입력점을 찾으라.
6. OAuth scope를 줄였으면 기존 refresh token의 실제 grant가 자동으로 줄지 않는다는 점까지 확인하고 재연결·폐기 절차를 남겨라.
7. 2차에서 새 발견사항이 나오면 수정·회귀 테스트 후 해당 공격 경로만 한 번 더 종단 확인하라.

## 10. 결과 보고

[report-format.md](references/report-format.md)를 따라 다음 순서로 보고하라.

1. 결론과 즉시 조치가 필요한 위험
2. 검토 범위와 검증 방법
3. 심각도순 발견사항
4. 하드닝 제안
5. 확인하지 못한 범위와 잔여 위험
6. 실행한 테스트와 결과

각 발견사항에 정확한 파일·줄, 공격 전제, 데이터 흐름, 영향, 최소 수정안, 수정 후 검증법을 포함하라. 코드 줄 근거가 없는 일반론은 발견사항으로 올리지 마라.

## 수정 모드

사용자가 수정을 요청했을 때만 다음을 수행하라.

1. 근본 원인을 가장 좁은 변경으로 수정하라.
2. 취약 동작을 실패시키는 회귀 테스트를 먼저 추가하거나 함께 추가하라.
3. 정상 역할·정상 입력의 기존 동작이 유지되는지 검증하라.
4. DB·토큰·세션·파일에 영향을 주면 마이그레이션·폐기·복구 절차를 함께 검토하라.
5. 수정 후 동일 공격 경로를 다시 추적하고 테스트 결과를 보고하라.
6. 독립적인 2차 감사에서 새 문제가 없거나 새 발견사항까지 수정·재검증된 뒤에만 완료로 보고하라.
